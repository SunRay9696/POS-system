# 架构与数据口径

这是单门店、本地演示 POS，包含 React / TypeScript 前端、Express API 与 Node.js 24 的 `node:sqlite` 数据层。开发时 Express 集成 Vite；构建后由同一服务提供静态页面。默认监听回环地址，尚未实现多门店、正式支付清算或生产运维能力。

## 订单与库存

菜单保存售价和食材配方。建立订单时由服务端计算金额，并快照餐品名称、售价与配方；客户端提交的价格、总额或付款状态不会决定账本数据。待付款订单不预留或扣减库存，不计入销售报表。

确认现金记账或模拟电子支付时，在同一 SQLite 事务内汇总所有配方用量、核验余量、扣料、写库存流水、快照销售成本，并更新付款状态与营业日期。任一食材不足会整体回滚。重复付款不会重复扣料；创建订单的请求编号用于幂等处理，同编号而不同订单内容会被拒绝。

进货按食材基础单位登记；新增采购成本和现有库存成本合并为加权平均单位成本。之后的销售使用付款时成本，已付款订单的成本快照不随后续采购改写。库存流水记录期初、销售扣料、入库及示例盘点调整；示例调整用于展示低库存提醒，不能视为真实门店损耗记录。

库存低于或等于补货线时产生提醒，建议补至目标库存。系统提供建议，不自动下采购单。菜单、食材和配方初始均为示例；投入实际使用前需核对门店的实际单位、用量、损耗和采购价格。

## 报表与经营助理

所有日期归属使用 `Asia/Kuala_Lumpur`。本日报表按当地营业日汇总；周报从周一至今；月报从当月一日至今。销售、产品排名与高峰统计只包含已付款订单，高峰由付款时间推算，不等同于实际到店人数。

账务口径：

```text
净销售额 = 已付款餐品金额 + 服务费（当前固定为零）
经营利润 = 净销售额 − 销售成本 − 所选期间录入的经营费用
实收总额 = 净销售额 + 代收税费
```

进货首先增加库存；出售时按配方计入销售成本，避免同时把同笔进货作为经营费用再次扣除。经营费用按录入日期归属。当前不是完整法定会计系统：不含所得税、折旧、退款、应收应付和其他未录入调整。默认零税率尚未确认实际 SST 义务。所有交易，包括现金方式，持续标记为演示数据。

三个助理共享同一账本：财务助理解释经营盈亏，库存助理提示补货，营业助理分析销量与付款高峰。数值由数据库和确定性计算产生。规则分析始终可用；可选 OpenAI 请求只解释经营汇总，不取得修改账本、采购、付款或发票提交权限。AI 输出是建议；模型故障不影响原有账目与规则报表。

## 访问、保存与外部接入

员工接口使用 PIN 登录、HttpOnly 会话 Cookie、基础失败次数限制和请求来源校验。员工会话保存在进程内，重启后失效。顾客只获取公开菜单并凭订单付款凭证进行模拟支付，不能读取员工报表、成本、配方或发票买方资料。这些措施是演示环境基础保护，不能替代生产身份与角色权限方案。

SQLite 默认保存至 `data/squarebox.sqlite`，启用外键、WAL 和事务。`data/`、`.env`、构建输出与依赖目录不提交 Git。运行中备份需使用 SQLite 一致性备份能力；离线备份先停止服务，并保留数据库及存在的 WAL 等关联文件。只复制活动主数据库文件不是可靠备份。

真实支付网关尚未接入，因此没有真实电子扣款或清算。e-Invoice 目前只保存并导出 `draft_not_submitted` 内部 JSON，不产生官方验证标识；详见 [MyInvois 说明](MYINVOIS.md)。跨设备二维码需要可达的 `PUBLIC_BASE_URL` 与部署配置。公开运营前需补齐 HTTPS／安全 Cookie、正式身份权限、支付、数据保护与运维验证。
